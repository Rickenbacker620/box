# 添加产品到产品库

把用户照片只用于识别，不把它作为产品主图。前端保持匿名只读；写入优先使用已连接并获授权的 Supabase 工具，不索取、展示或保存 `service_role`/secret key。

## 固定项目配置

- Supabase project ref：`rlyngocxosbmcylsxtvw`
- Storage bucket：`box-assets`
- 产品图片路径：`products/<brand-slug>/<product-slug>.png`
- 允许的分类：
  - `food`
  - `snack`
  - `ice-cream`
  - `drink`
  - `fragrance`
  - `personal-care`
  - `beauty`
  - `household`
  - `electronics`
  - `instant`
  - `yogurt`
  - `other`

不要自行创造近义分类，例如已有 `drink` 时不要写 `beverage`。

## 数据表

### `brands`

| 字段 | 类型 | 要求 |
| --- | --- | --- |
| `id` | text | 必填；26 位大写 Crockford Base32 ULID |
| `name` | text | 必填；品牌正式显示名；数据库唯一 |

### `products`

| 字段 | 类型 | 要求 |
| --- | --- | --- |
| `id` | text | 必填；26 位大写 Crockford Base32 ULID |
| `name` | text | 必填；包装或官网上的正式产品名 |
| `brand_id` | text | 必填；引用 `brands.id` |
| `category` | text | 必填；只能从固定分类中选择 |
| `rating` | integer | 必填；用户给出的 1–5 整数 |
| `comment` | text/null | 保留用户原意；未提供时写 `null`，不要写空字符串 |
| `image_url` | text/null | Storage 内对象路径，不是完整 URL |

ID 必须由合规 ULID 生成器生成并匹配 `^[0-9A-HJKMNP-TV-Z]{26}$`。不要使用 slug、时间戳字符串或随手编造的字符作为 ID；品牌和产品分别生成不同 ULID。

当前数据库只强制主键、`brands.name` 唯一和 `products.brand_id` 外键；它没有强制产品查重、分类枚举或评分范围。因此这些校验不能省略。

## 命名规则

### 显示名称

- 品牌名优先采用包装正面或品牌官网的正式拼写。
- 产品名优先采用包装或官网名称，去掉首尾空白，不翻译用户没有要求翻译的正式名称。
- 不为了统一大小写而改坏商标，例如保留 `Oatly`、`Häagen-dazs`。
- 用户照片看不清、不同市场名称冲突或口味无法确定时，先询问用户。

### Storage slug

品牌和产品分别生成 slug：

1. 转为小写。
2. Unicode 规范化并去除拉丁字母重音：`Häagen` → `haagen`。
3. `&` 转为 `and`。
4. 删除撇号和所有格符号：`Lay's` → `lays`，`Alec's` → `alecs`。
5. 空格、斜杠、下划线和其他非字母数字字符统一转为单个 `-`。
6. 合并连续 `-`，删除首尾 `-`。
7. 中文使用无声调拼音并按词分隔：`白象` → `bai-xiang`；产品中文名同理。
8. 日文、韩文或其他非拉丁文字使用稳定、可读的官方罗马字。无法可靠罗马化时先询问用户，不要生成空 slug 或随机字符串。
9. 单个 slug 最多 100 个字符；过长时先删除不影响识别的包装词，必须保留品牌内区分产品、口味、型号所需的信息。

示例：

| 显示名称 | slug |
| --- | --- |
| `Häagen-dazs` | `haagen-dazs` |
| `Lay's` | `lays` |
| `White Chocolate Raspberry Truffle Ice Cream` | `white-chocolate-raspberry-truffle-ice-cream` |
| `2合1烤虾海鲜酱味薯片` | `2-he-1-kao-xia-hai-xian-jiang-wei-shu-pian` |

最终路径示例：

```text
products/haagen-dazs/white-chocolate-raspberry-truffle-ice-cream.png
```

路径冲突时不要覆盖：

- 先确认是否其实是重复产品。
- 如果是不同规格或不同口味，把有意义的区别加入产品 slug，例如 `-zero-sugar`、`-12-oz`。
- 只有没有稳定描述可用时才添加 `-2`、`-3`。
- Storage 上传必须使用 `upsert: false` 或等价的“对象已存在即失败”行为。

## 执行流程

### 1. 收集并识别

从用户照片和消息中提取：

- 品牌
- 正式产品名与口味/型号
- 分类
- 1–5 整数评分
- 评价

不得从照片推测用户评分或评价。用户给出 4.5 等非整数评分时，说明表中只能存整数，请用户选择整数；不要自行四舍五入。

### 2. 查重

写入前用 Supabase 查询：

- 品牌：对 `trim(name)` 做不区分大小写的完全匹配。
- 产品：在同一品牌内，对 `trim(name)` 做不区分大小写的完全匹配。
- 再浏览同品牌下相似名称，防止因连字符、空格、口味顺序或拼写差异产生近似重复。

若已存在：

- 展示现有记录的名称、品牌、评分和评价。
- 停止新增。
- 如果用户实际想修改现有记录，明确说明本技能只负责新增，并在获得新的明确授权后再执行更新流程。

若品牌已存在，必须复用其 `id`。只有确认没有大小写或标点变体后才能新增品牌。

### 3. 寻找并处理产品图

按以下优先级寻找：

1. 品牌官网的产品图。
2. 制造商或官方经销商商品图。
3. 可信零售商的清晰包装图。

要求：

- 搜索结果必须与具体品牌、产品和口味/型号一致。
- 优先正面包装、纯色或透明背景、无水印的图片。
- 保存来源网页 URL 和最终图片直链，确认直链可公开 GET。
- 验证响应是实际图片，不能是 HTML、登录页、缩略图占位符或已失效防盗链。
- 下载图片后真正转换为 PNG；不能只把 `.jpg`/`.webp` 后缀改成 `.png`。
- 输出必须是静态 RGB/RGBA PNG，保持原始宽高比，不拉伸。
- 清晰图片建议最长边不超过 2000 px、文件不超过 5 MiB；较小但足够清晰的官方图不要强行放大。
- 去除 EXIF、定位信息和不必要元数据。
- 不使用用户拍摄的照片，除非用户明确改变要求。

如果找不到可靠图片，向用户展示情况，让用户选择提供图片或允许 `image_url = null`；不要随便配一张相似产品图。

### 4. 检查写入能力

在确认前只做只读查询和图片搜索。

- 优先使用已连接的 Supabase MCP/OAuth 工具。
- 不要求用户把 secret/service-role key 发到聊天中。
- 不把高权限 key 写入仓库、环境文件、命令输出或前端。
- 不给 `anon` 增加 INSERT、UPDATE、DELETE 权限。
- 不直接向 `storage.objects` 表插入记录。

若当前工具只能操作数据库、不能上传 Storage 对象，停止并说明缺少图片上传能力。请用户连接支持 Supabase Storage 上传的工具，或让用户先按指定路径上传图片。不能仅写数据库路径假装图片已上传。

### 5. 写入前确认

任何写操作前，向用户展示以下表格并等待明确确认：

| 项目 | 拟写入值 |
| --- | --- |
| 产品名 | 正式显示名 |
| 品牌 | 正式显示名 |
| 是否新品牌 | 是/否 |
| 分类 | 固定分类之一 |
| 评分 | 1–5 整数 |
| 评价 | 原文或 `null` |
| 品牌 slug | 计算结果 |
| 产品 slug | 计算结果 |
| Storage 路径 | `products/<brand-slug>/<product-slug>.png` |
| 图片来源 | 来源网页 URL |
| 图片预览 | 可访问的候选图 |

用户修改任何字段后，重新查重、重新计算 slug/path，并再次确认受影响的内容。

### 6. 上传并写入

用户确认后严格按顺序执行：

1. 再查一次产品与 Storage 路径，防止确认期间发生重复或冲突。
2. 把已转换的 PNG 上传到 `box-assets`，使用最终路径且禁止覆盖。
3. 验证对象存在、MIME 为 `image/png`、公开 URL 返回成功。
4. 复用现有品牌；若为新品牌，生成 ULID 后创建。
5. 生成新的产品 ULID并插入 `products`，`image_url` 只写对象路径。
6. 尽可能把品牌与产品数据库写入放在同一事务中。

若数据库写入失败：

- 删除本次刚上传的图片，避免孤儿对象。
- 只有在本次新建品牌且没有任何产品引用它时，才清理该品牌。
- 不删除或覆盖任何预先存在的对象或记录。
- 报告具体失败步骤，不宣称成功。

### 7. 完成后验证

必须完成以下验证：

- 按产品 ID 重新查询 `products`。
- join `brands`，确认品牌名称和 `brand_id`。
- 比较名称、分类、评分、评价和 `image_url` 与确认表完全一致。
- 请求 Storage 公开 URL，确认返回图片。
- 用 publishable/anon 身份做一次前端等价 SELECT，确认 RLS 下可读取。
- 确认同品牌同名称只有一条记录。

最后向用户报告：

- 已添加或因重复而跳过。
- 产品和品牌名称。
- 产品 ID。
- Storage 路径与可访问图片 URL。
- 若有任何降级（例如无图片），明确说明。
