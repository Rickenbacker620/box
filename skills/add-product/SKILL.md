# 添加产品到产品库

将用户提供的文字信息录入产品库。前端保持匿名只读；写入优先使用已连接并获授权的 Supabase 工具，不索取、展示或保存 `service_role`/secret key。

## 固定项目配置

- Supabase project ref：`rlyngocxosbmcylsxtvw`
- 已有的标准分类：
  - `food`
  - `snack`
  - `ice-cream`
  - `drink`
  - `fragrance`
  - `perfume`
  - `personal-care`
  - `shampoo`
  - `body-wash`
  - `beauty`
  - `household`
  - `electronics`
  - `instant`
  - `yogurt`

不要自行创造近义分类，例如已有 `drink` 时不要写 `beverage`。当现有分类均不合适时，必须先征询用户是否新增分类，获得明确同意后才能使用新分类。

## 数据表

### `brands`

| 字段 | 类型 | 要求 |
| --- | --- | --- |
| `id` | uuid | 主键；数据库以 `gen_random_uuid()` 自动生成 |
| `name` | text | 必填；品牌正式显示名；数据库唯一 |

### `products`

| 字段 | 类型 | 要求 |
| --- | --- | --- |
| `id` | uuid | 主键；数据库以 `gen_random_uuid()` 自动生成 |
| `name` | text | 必填；包装或官网上的正式产品名 |
| `brand_id` | uuid | 必填；引用 `brands.id` |
| `category` | text | 必填；使用已有分类，或由用户明确同意后新增 |
| `rating` | integer | 必填；用户给出的 1–5 整数 |
| `comment` | text/null | 保留用户原意；未提供时写 `null`，不要写空字符串 |

当前数据库只强制主键、`brands.name` 唯一和 `products.brand_id` 外键；它没有强制产品查重、分类枚举或评分范围。因此这些校验不能省略。

## 命名规则

- 品牌名优先采用包装正面、品牌官网或用户提供信息中的正式拼写。
- 产品名优先采用包装、官网或用户提供信息中的正式名称，去掉首尾空白，不翻译用户没有要求翻译的正式名称。
- 不为了统一大小写而改坏商标，例如保留 `Oatly`、`Häagen-dazs`。
- 产品名称、品牌或口味/型号无法确定时，先询问用户。

## 执行流程

### 1. 收集并确认产品信息

从用户消息中收集：

- 品牌
- 正式产品名与口味/型号
- 分类
- 1–5 整数评分
- 评价

不得自行推测用户评分或评价。用户给出 4.5 等非整数评分时，说明表中只能存整数，请用户选择整数；不要自行四舍五入。

缺少产品名、品牌、分类或评分时，先向用户询问；评价可以为空。

### 2. 匹配或新增分类

先查询 `products.category` 的去重列表，并与“已有的标准分类”一起作为可选分类。

- 若产品明确属于已有分类或其常用同义分类，使用既有的规范分类。
- 若没有合适分类，说明原因并向用户提出明确问题：`没有适合 <产品名> 的现有分类。要新增「<建议分类>」吗？`
- 仅当用户明确同意新增时，才在本次产品记录中写入该新分类。
- 用户不同意或未回答时，不写入产品；请用户从现有分类中选择或提供新的分类名称。

项目没有独立的分类表。获准的新分类将作为 `products.category` 的新文本值保存，并在前端从产品数据中自动成为可筛选项。

### 3. 查重并确认品牌

写入前用 Supabase 查询：

- 品牌：对 `trim(name)` 做不区分大小写的完全匹配。
- 产品：在同一品牌内，对 `trim(name)` 做不区分大小写的完全匹配。
- 再浏览同品牌下相似名称，防止因连字符、空格、口味顺序或拼写差异产生近似重复。

若已存在：

- 展示现有记录的名称、品牌、评分和评价。
- 停止新增。
- 如果用户实际想修改现有记录，明确说明本技能只负责新增，并在获得新的明确授权后再执行更新流程。

若品牌已存在，必须复用其 `id`。

若没有找到匹配品牌（包括大小写、空格与标点变体），必须先询问用户：`没有找到品牌「<品牌名>」。要创建这个新品牌吗？`

- 只有用户明确同意后，才可以将品牌标记为“新品牌”并进入写入前确认。
- 用户不同意或未回答时，停止写入，请用户选择已有品牌或更正品牌名。

### 4. 检查写入能力

确认前仅进行只读数据库查询。

- 优先使用已连接的 Supabase MCP/OAuth 工具。
- 不要求用户把 secret/service-role key 发到聊天中。
- 不把高权限 key 写入仓库、环境文件、命令输出或前端。
- 不给 `anon` 增加 INSERT、UPDATE、DELETE 权限。

若当前工具没有数据库写入能力，停止并说明需要已授权的 Supabase 写入工具；不要通过修改前端权限来绕过限制。

### 5. 写入前确认

任何写操作前，向用户展示以下表格并等待明确确认：

| 项目 | 拟写入值 |
| --- | --- |
| 产品名 | 正式显示名 |
| 品牌 | 正式显示名 |
| 是否新品牌 | 是/否 |
| 是否新增分类 | 是/否 |
| 分类 | 已有分类或经用户同意的新分类 |
| 评分 | 1–5 整数 |
| 评价 | 原文或 `null` |

用户修改任何字段后，重新查重，并再次确认受影响的内容。

### 6. 写入

用户确认后严格按顺序执行：

1. 再查一次产品，防止确认期间发生重复。
2. 复用现有品牌；仅在用户已明确同意且确认表标为“是”时创建新品牌。
3. 插入 `products`，让数据库自动生成产品 UUID。

若产品写入失败：

- 如果本次新建的品牌没有任何产品引用它，清理该品牌。
- 不删除或覆盖任何预先存在的记录。
- 报告具体失败步骤，不宣称成功。

### 7. 完成后验证

必须完成以下验证：

- 按产品 ID 重新查询 `products`。
- join `brands`，确认品牌名称和 `brand_id`。
- 比较名称、分类、评分和评价与确认表完全一致。
- 若本次新增分类，确认该分类已出现在 `products.category` 的去重列表中。
- 用 publishable/anon 身份做一次前端等价 SELECT，确认 RLS 下可读取。
- 确认同品牌同名称只有一条记录。

最后向用户报告：

- 已添加或因重复而跳过。
- 产品和品牌名称。
- 产品 ID。
